## 9. Recommendations / improvements

- **Free logic before the next feature.** 93% LUT and 95% LSRAM leaves no room. Options: drop the DDR probe from the production gateware (keep it as a variant), share the 6847 attribute logic, shrink the tape FIFOs (1024 -> 256 words is enough at the daemon's pace), cut the MSX1's ROM cache tags.
- **Daemon performance.** The main thread uses 50-90% of a core (picture compression, state pushes) and one register read costs about 17 µs. Move the frame work to a thread with a lower priority or to a C helper, send frame deltas only when changed, and keep the disk service on its own thread. Measure with the new latency counters before changing anything.
- **Put the machine's ROM requirements in the page**: grey out Power until the machine's ROMs are loaded and list what is missing (several "does not power on" reports were missing ROMs).
- **Per-machine key help** on the page (the hint line still says "CP-300" for every machine).
- **Tape polish:** a real tape position bar, auto-play when the machine's motor goes on, a `.tzx` loader (the common Spectrum format), `.cas` for CoCo with headers detection, and a recorder-to-`.cas` converter.
- **A regression script** that runs `MACH=0,6,7` and the daemon tests in one go (about 15 min) and refuses a package build when one fails.
- **Git hygiene:** the work is one long branch of WIP commits with release tarballs inside; squash into meaningful commits and keep tarballs out of git (use a releases folder outside the repo or GitHub releases) before pushing.
- **A CPU trace on the board for the CP-400**: the debug register gives one address at a time; a small trace FIFO (the last 256 addresses of the 6809 plus the I/O accesses) read by the daemon would find a hang like CALIXTOP's in one look. It costs a block RAM (trade it against the tape FIFOs).
- **Run the user's programs in XRoar first** (`C:\apps\XRoar`, ROMs in its `roms/` folder) to know the expected behaviour before debugging the FPGA; the Elite project's scripts (`Elite\CoCo\perf.sh`) show the options that work with ROMs.
- **Page code:** `index.html` is one 45 KB file; split the per-machine panels, and test it in a headless browser.

### 12.1 64 KB banked cartridges (the user's Elite port: `C:\Users\roniv\Dev\github\Elite\CoCo`, `build\elite.rom`, 65,536 bytes)

- **Mapper** (from `coco-source/engine/loader.asm`, `REPORT-COCO2-IMPROVEMENTS.md`): a "Super Program Pak style" banked ROM: **4 pages of 16 KB**, the page number written to **`$FF40`**, the selected page visible at `$C000-$FEFF` (63 sectors of 256 bytes per page, the top 256 bytes are hidden by the I/O area). The loader clears `$FF40` (page 0) at start and reads overlays from the ROM during the game (XRoar runs it as a `gmc` cartridge).
- **Why the core cannot do it today:** the cartridge is one 8 KB block (`cart_ra <= cpu_a(12 downto 2)`, 4 LSRAM) mirrored over `$C000-$FEFF`, there is no page register, and 64 KB in LSRAM would need 32 blocks (4 are free). The write to `$FF40` is also the floppy controller card's control register (`bvf_cocofdc`): with no disk image mounted the card is disabled (IDE_CFG b3 = 0), so `$FF40` is free; with both a banked cartridge and a floppy, the write would reach both, as on a real CoCo.
- **Design (recommended):** keep the ROM in DDR like the MSX1's (the daemon writes it with `ddr_write` at a window such as `$650000`) and read it through the same direct-mapped cache: (1) move the MSX1's cache and its `bvf_msxmem` AXI use into a module shared by machine (data store: the pool's cartridge blocks, tags: a 1K x 6 RAM, so no new block RAM); (2) a page register written at `$FF40`, cleared at reset: address = page * 16 KB + (cpu_a - $C000); (3) wait states on a miss: gate the 6809's `cpu_ena` while the cartridge data is not ready (the CPU repeats the same cycle on the next E, no change to the SAM); (4) the AXI ownership (`own`) must include the CP-400 when a banked cartridge is loaded; (5) daemon: `PUT /api/rom/cp400cart` accepts 8 / 16 / 32 / 64 KB, the 8 KB case stays in block RAM. Estimate: 250-350 LUT (headroom is about 1,300 at 94.3%: trim the DDR probe or the tape FIFOs first), no LSRAM. Test with a `MACH=8` bench (a 6809 program writes `$FF40` = 0..3 and reads four different pages), then Elite on the board.
- Other mapped cartridges (Multi-Pak style selection at `$FF7F`, other games) can use the same page-register idea with a different decode: read each ROM's loader before assuming `$FF40`.
